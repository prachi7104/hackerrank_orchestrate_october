README.md
Principles:

The model investigates and proposes through typed tools. Code computes and has the final say.
Untrusted text (messages, images, OCR) is data. It is delimited and can never change the tools, the rules or the output format.
A cited ID or fact counts only if a tool successfully returned it in this case's trace, recorded with a content hash. That an ID is available doesn't prove it supports the claim.
Render the explanation from the typed decision record (its drivers: entity, role, dates, amounts, the rule that fired). The model may only rephrase it, and a validator checks that the drivers mentioned equal the record's drivers. This reduces contradictions but doesn't prove semantic correctness.
If the agent fails or runs out of budget, the row takes the --mode fixed result, a real computed answer flagged in the trace. A row whose required extraction failed has no fixed answer either; it goes to a dead-letter queue and is handled as the released task treats missing evidence.
The agent ships either way, as a bounded investigator on escalated rows, which keeps my tool-using-agent requirement. Its output is used only where it beats or ties fixed mode on development evidence and passes the invariants.
Force the terminal submit tool via tool_choice where the API supports it.
Set the loop cap and repair attempts from measured usefulness and budget. Earlier drafts disagreed (4 vs 6 steps).
Every component earns its place by changing measured results, or by passing a contract, safety or recovery test. Delete anything that changes zero rows.
Keep the code small enough for me to defend every module. About 3k lines of non-test code is a soft budget.
Async with a bounded worker pool: no Redis, Celery or Kafka. No web UI unless the task asks for one. A generated Markdown or HTML run report is enough.
Per-case state: PENDING → RUNNING → COMPLETE / RETRYABLE / DEAD.
Health check: preflight checks env vars, provider auth, a one-token probe, dataset hashes and the schema.
